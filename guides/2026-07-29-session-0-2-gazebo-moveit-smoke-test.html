Session 0-1에서 이월된 규칙. rmw_zenoh_cpp는 별도 Zenoh router가 살아 있어야 ROS graph가 보입니다. 오늘은 터미널이 네 개 필요하며, 그중 하나는 router 전용으로 계속 잡아 둡니다. 이 전제를 빠뜨리면 Gazebo도 MoveIt도 “실행은 됐는데 아무것도 안 보이는” 상태가 됩니다.

Step A

AGazebo 실행

물리 시뮬레이터와 controller를 먼저 세웁니다. MoveIt은 이 위에 얹히는 계층이므로, 여기가 흔들리면 MoveIt 디버깅은 의미가 없습니다.

BashContainer (T1)
ros2 launch open_manipulator_bringup open_manipulator_x_gazebo.launch.py

A-1 · launch가 실제로 하는 일

공식 파일(open_manipulator_bringup/launch/open_manipulator_x_gazebo.launch.py, commit 32975f8)을 직접 읽고 정리한 내용입니다.

요소실제 동작
launch 인자world 하나뿐이며 기본값은 empty_world입니다. use_sim 인자는 이 launch에 없습니다. xacro에 use_sim=true가 이미 고정되어 있습니다.
world 확장자launch가 내부에서 <world> + .sdf를 붙여 gz_args로 넘깁니다. 따라서 world:=empty_world처럼 확장자 없이 줍니다. empty_world.sdf로 주면 .sdf.sdf가 됩니다.
gz 실행 옵션-v 1 -r. -r 덕분에 시작과 동시에 시뮬레이션이 재생되며, 이것이 /clock이 흐르는 이유입니다.
controller 순서entity spawn 종료 → joint_state_broadcaster → 그 종료 후 arm_controller와 gripper_controller. 이벤트 체인이라 순차적으로 올라옵니다.
bridgeros_gz_bridge가 /clock 하나만 연결합니다(rosgraph_msgs/msg/Clock). 카메라·contact 등 다른 bridge는 Session 0-3의 몫입니다.
사용 가능한 worldopen_manipulator_bringup/worlds/에는 empty_world.sdf 하나만 있습니다.

이 launch에는 RViz가 없습니다. 공식 파일에서 RViz 노드는 주석 처리되어 있습니다. 오늘 보게 될 RViz는 전부 Step B의 MoveIt launch가 띄우는 것입니다. Gazebo만 띄운 상태에서 RViz가 없다고 실패로 판정하지 마십시오.

A-2 · 확인 (T3)

BashContainer (T3)
ros2 node list
ros2 topic list | grep -E '^/clock$|^/joint_states$|^/tf$|^/tf_static$'
ros2 control list_controllers --spin-time 5
ros2 topic echo /joint_states --once --timeout 10

기대값은 joint_state_broadcaster, arm_controller, gripper_controller 세 개가 모두 active인 상태입니다. 공식 image robotis/open-manipulator:5.0.0에서 ros2 control CLI가 설치된 것도 사전 확인했습니다. 명령이 없다면 임의 설치로 덮지 말고 Step 0-3의 기준 환경 차이로 기록합니다.

A-3 · Gazebo만 실패할 때

증상분리 시험
gz sim 창이 아예 안 뜸Session 0-1의 GUI 전제부터 재확인합니다. container에서 rviz2가 떴는지, DISPLAY가 살아 있는지 봅니다.
창은 뜨는데 검거나 깨짐LIBGL_ALWAYS_SOFTWARE=1을 붙여 software rendering으로 분리합니다. 이때만 뜬다면 GPU 경로 문제로 기록합니다.
로봇이 안 보임ros2 node list에 robot_state_publisher가 있는지, spawn 로그에 오류가 없는지 확인합니다.
controller가 안 올라옴T1 로그에서 spawner 순서를 따라갑니다. joint_state_broadcaster가 실패하면 뒤의 두 controller는 시작조차 하지 않습니다.
Step B

BMoveIt과 RViz

Gazebo가 안정된 뒤에 띄웁니다. 두 창은 끝까지 동시에 유지되어야 합니다.

BashContainer (T2)

use_sim:=true를 생략하지 마십시오. 공식 launch에서 use_sim의 기본값은 false입니다. 생략하면 move_group과 RViz의 use_sim_time이 false가 되어 Gazebo의 /clock과 시간 기준이 달라집니다.

두 값 모두 true여야 합니다. false라면 use_sim:=true를 빠뜨린 것이므로 T2를 종료하고 다시 실행합니다.

공식 launch의 URDF fallback 경고. 시작 로그에 Cannot infer URDF와 robot description will be loaded from /robot_description topic이 함께 나타날 수 있습니다. 설치된 공식 launch를 --show-args로 읽을 때도 재현된 경고입니다. 경고 한 줄만으로 실패 판정하지 말고, /move_group과 /rviz2_moveit가 실제로 올라오고 RViz에 RobotModel이 표시되는지로 판정합니다.

MoveIt만 실패할 때. 커리큘럼의 지시대로 Gazebo와 controller를 먼저 분리 검증합니다. Step A-2에서 세 controller가 active였다면 문제는 MoveIt 쪽이고, 아니라면 문제는 아래층에 있습니다. 두 층을 동시에 만지지 마십시오.

Step C

Carm과 gripper 조작

커리큘럼 실습 1~6에 해당합니다. RViz의 Motion Planning 패널에서 수행합니다.

C-1 · SRDF에 실제로 정의된 이름

아래는 open_manipulator_moveit_config/config/open_manipulator_x/open_manipulator_x.srdf를 직접 확인한 값입니다. RViz의 Goal State 드롭다운에 이 이름들이 그대로 나타납니다.

Planning groupNamed state관절 값
arm
joint1~4 + end_effector_joint		initjoint1~4 모두 0 — 곧게 선 자세
homejoint1 0, joint2 -1, joint3 0.7, joint4 0.3
gripper
left 명령 + right mimic		opengripper_left_joint 0.019
closegripper_left_joint -0.01

C-2 · 실행 순서

  1. RViz 좌측 MotionPlanning → Planning 탭을 엽니다.
  2. Planning Group을 arm으로 선택합니다.
  3. Goal State를 home으로 두고 Plan → 궤적 미리보기 확인 → Execute.
  4. Gazebo 창에서 실제 로봇이 같은 자세로 움직이는지 눈으로 확인합니다.
  5. 다시 Goal State를 init으로 두고 Plan → Execute.
  6. Planning Group을 gripper로 바꾸고 open → Plan & Execute, 이어서 close.

C-3 · MoveIt ↔ controller 연결 계약

moveit_controllers.yaml과 hardware_controller_manager.yaml에서 확인한 값입니다.

ControllerMoveIt 인터페이스action namespace대상 관절
arm_controllerFollowJointTrajectoryfollow_joint_trajectoryjoint1, joint2, joint3, joint4
gripper_controllerGripperCommandgripper_cmdgripper_left_joint
BashContainer (T3)
ros2 action list | grep -E \
  '^/(arm_controller/follow_joint_trajectory|gripper_controller/gripper_cmd)$'
ros2 topic echo /joint_states --once --timeout 10

right joint는 확인된 mimic입니다. 공식 URDF와 simulation용 ros2_control xacro 모두 gripper_right_joint → gripper_left_joint, multiplier 1을 정의합니다. 따라서 controller는 left 하나만 명령하고 right는 같은 관절값을 따라갑니다. 두 관절의 axis 방향이 반대라 실제 손가락은 좌우 대칭으로 움직입니다. ros2 topic echo /joint_states --once로 open/close 전후 두 관절 값을 각각 기록해 이 계약이 런타임에서도 지켜지는지 확인합니다.

Step D

D토픽·시간·재현

커리큘럼 실습 7~9이자, 완료 기준의 절반이 걸린 구간입니다.

D-1 · 네 개 토픽 확인

BashContainer (T3)
ros2 topic echo /joint_states --once --timeout 10
ros2 topic echo /tf_static --once --timeout 10 \
  --qos-durability transient_local
ros2 topic hz /tf
ros2 topic echo /clock --once --timeout 10
ros2 topic hz /clock

ros2 topic hz 두 명령은 각각 10초 이상 관찰한 뒤 Ctrl+C로 종료하고 표시된 평균 Hz를 기록합니다. /tf_static은 이미 게시된 정적 변환을 받도록 transient_local durability를 명시했습니다. /clock은 Gazebo가 재생 중일 때만 흐릅니다. Gazebo GUI에서 일시정지를 눌렀다면 hz가 0으로 떨어지므로, 값이 이상하면 시뮬레이터 재생 상태부터 봅니다.

D-2 · sim time 정합성

노드확인기대
/move_groupros2 param get /move_group use_sim_timetrue
/rviz2_moveitros2 param get /rviz2_moveit use_sim_timetrue
/robot_state_publisherros2 param get /robot_state_publisher use_sim_timefalse 예상 — 공식 Gazebo launch가 설정하지 않음

robot_state_publisher=false만으로 실패가 아닙니다. Gazebo launch 파일을 읽어 보면 robot_state_publisher에는 robot_description만 전달되고 use_sim_time은 명시되어 있지 않습니다. 값 자체를 억지로 true로 고치지 말고 /tf 수신과 RViz의 TF 경고 유무를 함께 관찰합니다. 실제 불일치가 있을 때만 공식 launch의 문제 후보로 기록하고 Session 0-3 이후의 항목으로 넘깁니다.
