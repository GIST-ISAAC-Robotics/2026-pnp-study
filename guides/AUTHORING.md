# 일일 실행 가이드 작성 지침

이 문서는 `guides/`의 HTML 실행 가이드를 새로 만들거나 고칠 때 적용하는 공통 기준이다. 목표는 설명을 많이 싣는 것이 아니라, 처음 참여한 사람이 가이드 한 장만 보면서 **지금 어느 창에서 무엇을 하고, 무엇이 보이면 다음으로 가도 되는지** 판단하게 만드는 것이다.

## 1. 근거 우선순위

내용이 충돌하면 다음 순서로 판단한다.

1. `curriculum.md`의 현재 실행 계약과 Gate
2. 저장소의 실제 소스·설정·`progress.md`·전문 문서
3. 현재 컨테이너에서 확인한 버전·경로·runtime 결과
4. 이전 회차의 최신 가이드
5. 디자인 참고 자료

초안, 작성 도구, 작성자 사이의 비교는 가이드에 적지 않는다. 실습자에게 필요한 것은 최종 절차와 판정 기준이다.

## 2. 구성 원칙

모든 회차에 같은 목차나 단계 수를 강제하지 않는다. 학습 목표와 실습 규모에 맞게 순서를 정하되, 처음 참여한 사람이 다음 내용을 놓치지 않게 한다.

- 이번 회차에서 이해하거나 만들어 볼 대상
- 명령을 실행할 환경이나 창
- 그대로 실행할 수 있는 명령과 관찰할 핵심 결과
- 실습을 마쳤다고 판단할 기준과 필요한 정리

창 배치, 준비물, 완료 기준, 개념 설명은 별도 절로 둘 수도 있고 해당 단계 안에서 바로 안내할 수도 있다. 설치 중심 회차와 코드 실습 회차를 억지로 같은 형식에 맞추지 않는다.

## 3. 초보자용 설명 규칙

- 명령 바로 앞에 “이 명령이 무엇을 바꾸는지”와 “어느 창에서 실행하는지”를 적는다.
- 코드 블록은 그대로 복사해 실행할 수 있어야 한다. 줄임표(`...`)로 필수 인자를 생략하지 않는다.
- 한 코드 블록에서 사용자가 해야 할 입력이 추가로 있다면, 블록 아래가 아니라 실행 전에 먼저 알린다.
- host 명령과 container 명령을 같은 블록에 섞지 않는다.
- prompt 예시는 `user@host:~$`와 `root@container:/workspace#`처럼 서로 다르게 보여준다.
- 출력 전문보다 다음 단계 판단에 필요한 핵심 줄을 보여 준다. 환경에 따라 달라지는 PID·timestamp·소수점은 “값은 달라도 됨”이라고 표시한다.
- 성공 기준에는 초록 체크 문구를, 중단 조건에는 명시적 경고를 둔다.
- 오류 해결은 오류 문자열 → 의미 → 복구 명령 → 재확인 순서로 쓴다.
- 익숙하지 않은 용어는 첫 등장 때 한 문장으로 정의한다. 예: “topic은 노드 사이에 계속 흐르는 이름 붙은 데이터 통로다.”
- “확인한다”, “적당히 수정한다”만 쓰지 말고, 실제 확인 명령과 기대 결과를 함께 쓴다.

## 4. 코드와 제공 파일

- 짧고 반드시 실행할 명령은 본문에 펼쳐 둔다.
- 긴 Python·YAML·XML·launch 전문은 `<details>`로 접되, 제목에 파일 경로와 역할을 쓴다.
- 긴 코드를 직접 타이핑하게 하지 않는다. `guides/assets/session-X/`에 검증한 파일을 두고 `cp` 명령으로 복사하게 한다.
- 제공 파일을 복사한 뒤에는 `sed -n`, `head`, `grep` 등으로 핵심 줄을 확인하게 한다.
- 모든 코드 블록에는 언어, 실행 위치, 복사 버튼을 둔다.
- 실습 중 임시로 설정을 바꾸면 원본 백업과 원복 명령을 같은 단계에 제공한다.
- 실행 파일은 syntax 검사와 실제 build 대상에 포함한다.

## 5. terminal 안내

여러 창을 동시에 써야 한다면 각 창의 실행 위치와 역할을 쉽게 구분할 수 있게 안내한다. `T0`, `T1` 같은 이름, 표, 카드, 단계 안의 짧은 문장 중 회차에 가장 잘 맞는 방식을 선택한다. 상주 명령과 다음 명령을 입력할 창이 헷갈릴 가능성이 있으면 진입·종료 방법을 가까운 위치에서 다시 보여 준다.

## 6. 검증 수준 표시

검증했다는 표현은 아래 네 수준을 섞지 않는다.

| 수준 | 의미 |
|---|---|
| 문서 검토 | 커리큘럼·이전 기록과 내용이 모순되지 않는지 확인 |
| 정적 검증 | HTML·JSON·Python·YAML·XML 문법과 링크 확인 |
| 화면 검증 | 실제 브라우저에서 desktop/mobile 레이아웃, 접기, 복사, anchor 확인 |
| runtime 검증 | 현재 ROS container에서 build·launch·가이드의 주요 예제를 실제 실행 |

안전하고 되돌릴 수 있는 범위라면 제작 과정에서 syntax 검사에 그치지 않고 임시
workspace의 build, 최소 실행, 핵심 메시지·종료 코드 확인 같은 간단한 runtime 검증을
직접 수행해도 된다. 이때 현재 실습 workspace와 사용자 산출물을 덮어쓰지 않으며,
검증하지 못한 부분은 검증한 것처럼 표현하지 않는다.

가이드 본문에는 “제작 과정에서 검증 결과가 이렇게 나왔다” 같은 사전 검증 보고서를
끼워 넣지 않는다. 본문에는 실습자가 판단할 수 있는 예상 출력·완료 기준만 자연스럽게
배치하고, 제작자의 검증 범위와 결과는 PR 설명이나 작업 완료 보고에서 필요한 만큼만
분리해 알린다.

## 7. 웹 디자인 규칙

원본 디자인 참고는 [`design/crimson2.md`](./design/crimson2.md)다. 다만 실제 웹 가이드의 기준은 이미 게시된 최신 가이드들이므로, 새 회차마다 시각 체계를 다시 설계하지 않는다. 직전 가이드와 가이드 목록에서 공통으로 쓰는 색상 토큰, 본문 폭, 여백, 글자 위계, 카드, 코드 블록, 접기, 복사 버튼, 진행 표시 방식을 먼저 재사용한다.

- 새 가이드는 기존 가이드의 CSS 토큰과 컴포넌트 스타일을 기본값으로 삼고, 회차 내용에 필요한 부분만 확장한다.
- 새로운 UI 패턴이 필요하면 기존 패턴과 나란히 비교하여 색상·간격·모서리·그림자·상호작용이 같은 사이트의 일부처럼 느껴지는지 확인한다.
- 이전 가이드와 디자인 참고 자료가 다르면 웹에서 실제 사용 중인 일관된 패턴을 우선한다. 접근성이나 가독성을 개선할 명확한 이유가 있을 때만 공통 스타일을 함께 갱신한다.

- 색상 토큰은 직전 가이드에서 사용한 기능성 crimson, 잉크, 중립 배경 값을 그대로 재사용한다. 사이트 전체의 공통 색상을 바꿀 때는 특정 회차 하나만 바꾸지 말고 기존 가이드도 함께 갱신한다.
- crimson은 진행 상태·링크·핵심 강조에 쓰고, 여러 accent 색을 장식용으로 섞지 않는다.
- prismatic gradient는 필요하면 hero의 큰 분위기 층에만 아주 약하게 쓴다. 버튼·배지·카드의 기능 색으로 쓰지 않는다.
- 고정 16:9 canvas, 고정 좌표 배치, presentation 전용 body lock은 사용하지 않는다. 본문은 반응형 단일 문서로 만든다.
- 카드에는 얇은 hairline과 절제된 겹그림자를 사용한다.
- 긴 본문은 최대 폭을 제한하고, mobile에서는 표와 코드를 가로 스크롤할 수 있게 한다.
- Pretendard를 우선하고, 시스템 sans-serif fallback을 둔다.
- 접기 아이콘의 `+`·`−`는 글자 baseline에 의존하지 않고 CSS 선을 중앙 정렬한다.
- keyboard focus, 색 대비, `aria` label을 포함한다.
- print에서는 navigation·복사 버튼을 숨기고 본문과 접힌 코드가 읽히게 한다.

## 8. 브라우저 점검표

- [ ] 첫 화면에서 회차, 목적, 예상 시간, 현재 단계가 보인다.
- [ ] 목차 anchor가 올바른 section으로 이동한다.
- [ ] 복사 버튼이 해당 코드만 복사하고 완료 상태를 표시한다.
- [ ] 접기 아이콘의 가로·세로 선이 원 중앙에 맞는다.
- [ ] 1440px 안팎 desktop과 390px 안팎 mobile에서 본문이 잘리지 않는다.
- [ ] 표와 긴 command는 페이지 전체를 밀어내지 않고 자체 스크롤된다.
- [ ] 체크박스 진행 상태가 새로고침 후 유지된다.
- [ ] 접힌 긴 코드는 인쇄 화면에서 펼쳐진다.

## 9. 게시 절차

1. 파일명은 가이드 제작일 기준 `YYYY-MM-DD-session-X-주제.html`로 정한다.
2. `guides/guides.json` 배열 맨 앞에 항목을 추가하고 `updated`를 바꾼다.
3. `guides/README.md`의 현재 가이드 표를 갱신한다.
4. 필요한 경우 루트 `index.html`의 최신 가이드 카드만 갱신한다.
5. 정적 검사, 화면 검사, 요청된 runtime 검사를 구분해 수행한다.
6. 변경 파일을 정확한 경로로 stage하고 commit·push·PR로 게시한다.

## 10. 문체와 금지 항목

- 한국어 존댓말과 명확한 명령형 안내를 사용한다.
- 특정 작성자·도구·초안의 존재를 전제하지 않는다.
- 캐릭터 호칭, 내부 별칭, 과도한 농담을 문서·활동 기록·commit·PR에 넣지 않는다.
- 실패를 성공처럼 축약하지 않는다. “명령 일부 실행”, “메시지 수신”, “완료 기준 통과”를 구분한다.
- 아직 실행하지 않은 회차의 결과를 미리 채우지 않는다.
