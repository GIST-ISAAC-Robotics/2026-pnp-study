Action과
3층 상태기계 골격

오래 걸리는 작업을 요청하고, 진행 단계를 feedback으로 보고, 취소와 timeout을 구분하는 두 단계 action 체인을 만듭니다. 오늘의 inner server는 로봇을 움직이지 않는 dummy입니다.

예상 3~4시간 ROS 2 Jazzy · Python RunTrial → PickPlace 실행 창 T0~T4
먼저 큰 그림

요청 하나를 두 action과 세 책임 계층으로 나눕니다

Service는 짧은 요청·응답에 적합하지만, 픽앤플레이스처럼 오래 걸리고 중간 진행률과 취소가 필요한 작업은 Action으로 표현합니다. 상태기계는 “지금 어느 단계이며 다음에 어디로 갈 수 있는가”를 코드로 제한합니다.

Session 4 전까지 로봇 동작 없음
Action

goal을 받고 feedback을 보내며 최종 result 또는 cancel terminal을 반환합니다.

State machine

허용된 전이만 통과시켜 단계 소유권과 실패 위치를 명확하게 합니다.

Heartbeat

/task/status가 2 Hz로 증가해야 active task가 살아 있다고 판단합니다.

trial_completed

성공 여부가 아니라 기록 가능한 terminal과 필요한 cleanup이 끝났다는 뜻입니다.

pipeline_success

요청한 scope의 필수 stage가 모두 성공하고 error code가 0이라는 뜻입니다.

SAFE_STOP

inner terminal을 확인하지 못한 경우 다음 reset·goal을 막고 수동 복구를 기다립니다.

오늘 Gazebo·MoveIt·로봇은 실행하지 않습니다. 실제 pnp_manipulation 패키지는 Session 4에서 만듭니다. 오늘은 pnp_evaluation/test/dummy_pick_place_server.py가 inner action 계약만 흉내 냅니다.

왜 pose가 세 종류인가요? object / pick / place
  • object_pose: collision object 중심 pose입니다.

성공·코드화된 실패·manual cancel과 timeout 경계가 서로 다른 terminal 의미로 남습니다.
